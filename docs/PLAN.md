# AI 공감 다이어리 앱 작업 계획

이 문서는 `.claude/agents`의 에이전트 5개에게 역할을 나눠 맡기는 단계별 작업 계획이다. 계획만 담고 있으며, 각 단계는 사용자가 진행하라고 지시할 때 시작한다.

## 요구사항 요약

- **누가**: 구글 계정으로 로그인한 사용자. 로그인은 Auth.js로 하고, 사용자는 자기 일기만 볼 수 있어야 한다.
- **무엇을**: 한 줄 일기 쓰기, 감정 분석과 공감 메시지, 지난 기록 보기. 일기에 자해나 극단적 선택 같은 위기 표현이 있으면 공감 메시지와 함께 전문 상담 연락처를 안내한다.
- **어떻게**: Next.js로 만들고, 일기는 `.env`의 `DATABASE_URL`이 가리키는 Supabase Postgres에 `diary` 스키마를 새로 만들어 저장한다. 다른 스키마의 표는 건드리지 않는다.
- **AI 모델**: OpenRouter의 `nvidia/nemotron-3-ultra-550b-a55b:free`를 먼저 부르고, 응답이 없거나 오류가 나면 `nvidia/nemotron-3.5-super-vl:free`로 넘어간다. API 키는 `.env`의 `OPENROUTER_API_KEY`를 쓴다.
- **어디에**: 깃허브 저장소 `ai-empathy-diary-ch7`에 올리고 Vercel에 배포한다.
- **느낌**: 따뜻하고 편안한 일기장 화면.

## 지켜야 할 제약

- `diary` 스키마 밖의 표는 어떤 단계에서도 읽거나 고치지 않는다.
- `.env`는 열거나 값을 화면에 출력하지 않고, 변수 이름(`DATABASE_URL`, `OPENROUTER_API_KEY`)만 코드와 설정에서 참조한다.
- 위기 표현 감지와 상담 안내는 2단계(AI 연동)부터 4단계(QA)까지 빠짐없이 다룬다.

## 0단계: PRD

- **맡을 에이전트**: product-manager
- **할 일**: 위 요구사항을 바탕으로 PRD를 쓴다. 목표, 사용자, 기능 범위(한 줄 일기, 감정 분석과 공감 메시지, 지난 기록, 위기 표현 안내), 비목표, 성공 기준을 담는다.
- **산출물**: `docs/PRD.md`
- **끝났는지 확인하는 법**: `docs/PRD.md`가 생기고, 그 안에 로그인 방식(구글, Auth.js)과 사용자별 격리, 기능 3가지, 위기 표현 처리, AI 모델 호출 순서, DB 스키마 제약, 배포 대상(깃허브 저장소, Vercel)이 모두 적혀 있는지 읽어서 확인한다. 빠진 항목이 있으면 product-manager에게 보완을 요청한다.

## 1단계: 뼈대

- **맡을 에이전트**: backend-developer(주도), frontend-developer(보조)
- **할 일**: Next.js 프로젝트를 만들고 폴더 구조를 잡는다. Auth.js에 구글 공급자를 설정하는 틀을 만들고, `.env`의 `DATABASE_URL`로 Supabase에 연결해 `diary` 스키마와 일기 표를 만든다. 로그인 화면과 빈 메인 화면 등 기본 라우팅만 둔다.
- **끝났는지 확인하는 법**: `npm run dev`로 뼈대가 뜨고 로그인 화면이 보이는지 확인한다. Supabase에 `diary` 스키마와 표가 생겼는지, 다른 스키마는 그대로인지 확인한다. 코드에 `.env` 값이 그대로 적혀 있지 않고 변수 이름으로만 참조하는지 확인한다.

## 2단계: 백엔드·AI·화면 동시 진행

- **맡을 에이전트**: backend-developer, ai-integration-specialist, frontend-developer (병렬로 진행)
  - backend-developer: 일기 저장·조회 API, Auth.js 로그인 완성, 사용자별 데이터 격리(본인 글만 조회되게 쿼리와 권한을 건다)
  - ai-integration-specialist: OpenRouter 호출 로직(1차 `nvidia/nemotron-3-ultra-550b-a55b:free`, 무응답이나 오류 시 2차 `nvidia/nemotron-3.5-super-vl:free`로 전환), 감정 분석과 공감 메시지 프롬프트, 위기 표현 감지와 상담 연락처 안내 문구
  - frontend-developer: 일기 작성 화면, 지난 기록 화면, 로그인 화면. 따뜻하고 편안한 느낌의 디자인, 반응형, 웹 접근성
- **끝났는지 확인하는 법**: 세 에이전트가 각자 담당 모듈을 다른 모듈과 연결하지 않고 따로 확인한다.
  - backend: API를 직접 호출해 저장과 조회가 되고, 다른 사용자 계정으로는 조회되지 않는지 확인
  - ai-integration: 1차 모델이 실패했다고 가정했을 때 2차 모델로 넘어가는지, 위기 표현이 담긴 문장을 넣었을 때 상담 안내가 나오는지 확인
  - frontend: 더미 데이터로 화면을 띄워 레이아웃과 반응형, 접근성이 깨지지 않는지 확인

## 3단계: 통합

- **맡을 에이전트**: backend-developer(주도), frontend-developer·ai-integration-specialist(협조)
- **할 일**: 화면, API, AI 응답을 하나로 연결한다. 로그인부터 일기 작성, 감정 분석과 공감 메시지 수신, 지난 기록 보기까지 전체 흐름을 잇는다.
- **끝났는지 확인하는 법**: 구글 로그인부터 한 줄 일기 작성, 공감 메시지 표시, 지난 기록 확인까지 끊기지 않고 되는지 직접 실행해 본다. 다른 구글 계정으로 로그인했을 때 이전 계정의 일기가 보이지 않는지 다시 확인한다.

## 4단계: QA

- **맡을 에이전트**: qa-engineer
- **할 일**: 기능 시험(로그인, 일기 작성, 조회), 오류 처리 검증(OpenRouter 1차 모델이 실패했을 때 2차로 넘어가는지, 빈 입력이나 아주 긴 입력), 위기 표현이 담긴 일기로 상담 안내가 뜨는지 확인, 사용자 간 데이터 격리 재확인, 코드 리뷰로 버그와 고칠 점을 찾는다.
- **끝났는지 확인하는 법**: qa-engineer가 찾은 문제를 심각도별로 정리해 보고받는다. 치명적인 문제가 모두 고쳐졌는지 재확인할 때까지 이 단계를 반복한다.

## 5단계: 배포

- **맡을 에이전트**: backend-developer(주도)
- **할 일**: 변경 사항을 깃허브 저장소 `ai-empathy-diary-ch7`의 `main` 브랜치에 올린다. Vercel 프로젝트를 연결하고, `OPENROUTER_API_KEY`와 `DATABASE_URL` 등 환경변수를 Vercel에 등록한 뒤 배포한다.
- **끝났는지 확인하는 법**: 로컬 빌드나 테스트 통과만으로 끝낸 것으로 보지 않는다. 실제로 배포된 Vercel 주소를 열어, 구글 로그인부터 일기 작성, 공감 메시지 수신, 지난 기록 보기까지 직접 눌러서 스모크 테스트를 한다.
